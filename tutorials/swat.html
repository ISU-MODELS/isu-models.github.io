    SWAT

    A first successful run of classic SWAT2012, revision 695, on Windows. You download the Texas A&M executable, copy the lab’s example TxtInOut folder, run Rev_695_64rel.exe from that folder, and read FLOW_OUT in output.rch. SWAT+ is installed elsewhere on this host; this path is the 2012 engine.

    1. What this model does

    SWAT is a continuous, daily, watershed-scale water and water-quality model. Land is grouped into HRUs (unique land use, soil, and slope). HRUs drain to subbasins. Subbasins send water, sediment, and nutrients into reaches, and the reaches connect to an outlet. You will open the reach file first.

    The lab’s pinned engine is Rev_695_64rel.exe (SWAT2012 Rev. 695, 64-bit, 12 Feb 2025). ArcSWAT, QSWAT, and SWAT Editor can build a new project; they are not required to finish this tutorial.

    2. Get the software

    Download SWAT2012 rev. 695 from Texas A&M AgriLife. The software page also hosts ArcSWAT, QSWAT, and SWAT Editor. New projects are steered toward SWAT+; keep 2012 when you are repeating an existing TxtInOut tree, which is this lab’s case.

    SWAT2012 executables All SWAT software Documentation

    On this host the tree is already at C:\Grok\Models\installs\SWAT. If you are repeating the lab path, you can skip the download and use that folder.

    3. The lab install

    Classic SWAT is a folder of text files plus one executable. GIS is optional.

    installs\SWAT\golden holds a prior CLI tree. The verification below used a new working copy of the example inputs, so that golden tree stays untouched. tools\test_all_models.ps1 still runs in place under example; the tutorial wrapper below uses a disposable folder.

    4. Novice path: run the seven-subbasin example

    The example is a twenty-year continuous run (2001–2020) with two years skipped in the printed output. IPRINT is daily. You will copy the inputs into a fresh folder, drop the executable beside them, and run from that folder.

    $src = "C:\Grok\Models\installs\SWAT\example"
$run = "C:\Grok\Models\installs\SWAT\tutorial_run_20260913"
New-Item -ItemType Directory -Force -Path $run | Out-Null
Get-ChildItem $src -File | Where-Object {
  $_.Name -notlike "output.*" -and $_.Name -notlike "bmp-*" -and $_.Extension -notin ".out"
} | Copy-Item -Destination $run
Copy-Item "C:\Grok\Models\installs\SWAT\Rev_695_64rel.exe" $run -Force
Set-Location $run
.\Rev_695_64rel.exe

    On this host you can instead rerun the lab wrapper, which copies those inputs, executes the engine, asserts the numbers below, and rewrites the figure:

    python C:\Grok\Models\tools\run_swat_tutorial_verify.py

    Stand in the folder that contains file.cio. The engine does not take a project path on the command line. If you run it from a tools directory, it will not see the example watershed.

    5. Confirm the run

    The console should end with Execution successfully completed. Then open output.rch. Reach 7 is the outlet.

    CheckWhereThis verification (13 Sep 2026)
    Console run_stdout.txt Execution successfully completed (years 1–20)
    output.rch size run folder 33.8 MB (daily print, 18 years × 7 reaches)
    Outlet first-day FLOW_OUT REACH 7, day 1 0.5102 cms
    Outlet mean daily flow REACH 7, 2003–2020 1.0875 cms
    Outlet mean annual sediment REACH 7 SED_OUT 5,942 t/yr

    The automated test is test_tutorial_run inside tools\run_swat_tutorial_verify.py. It requires the success phrase, seven reaches, eighteen printed years, and REACH 7 first-day FLOW_OUT equal to 0.5102 cms within 0.0005. The older test_all_models.ps1 SWAT block still looks for a historic 0.2635E+01 token on the first data line of the standing example folder; use the wrapper above when you want a disposable copy of the current inputs.

    The 13 Sep 2026 run wrote eighteen printed years after the two-year skip. Outlet mean daily flow is 1.09 cms; 2006 is the wet peak. Mean annual sediment at reach 7 is 5,942 t/yr, with 2006 the high year on the right-hand panel.

    Model Input and Output

    Same-type files that only change location or ID are shown once. The count under each name is how few and how many of that type a run can hold. The example name is one file from the verification folder.

    Executable

    Rev_695_64rel.exe

    How many: exactly 1. This run: 1. Example: Rev_695_64rel.exe.

    This is the SWAT2012 revision 695 release engine. Start one copy in the TxtInOut folder. It reads file.cio and writes output.rch there. Open the example file in the verification folder to see that layout on disk.

    other SWAT*.exe

    How many: 0 to infinite. This run: 2. Example: SWAT.exe.

    Extra SWAT binaries can sit in the example folder, including debug builds. The verified path starts only Rev_695_64rel.exe. Open the example file in the verification folder to see that layout on disk.

    Input files

    file.cio

    How many: exactly 1. This run: 1. Example: file.cio.

    This is the master control file. It names weather files, databases, years, and fig.fig. One cio file per TxtInOut folder. Open the example file in the verification folder to see that layout on disk.

    fig.fig

    How many: exactly 1. This run: 1. Example: fig.fig.

    This is the watershed command file: the order of subbasins and routing so SWAT knows how land drains to the outlet. One fig file. Open the example file in the verification folder to see that layout on disk.

    basins.bsn

    How many: exactly 1. This run: 1. Example: basins.bsn.

    This is watershed-wide parameters such as runoff method and snow. One basin file for the whole project. Open the example file in the verification folder to see that layout on disk.

    basins.wwq

    How many: 0 to 1. This run: 1. Example: basins.wwq.

    This is watershed in-stream water-quality parameters not tied to a single reach file. At most one wwq file. Open the example file in the verification folder to see that layout on disk.

    *.pcp precipitation

    How many: 1 to infinite. This run: 1. Example: pcp1.pcp.

    This is measured daily precipitation. file.cio sets how many pcp files (NRGAGE). At least one. More files if you split gauges. Open the example file in the verification folder to see that layout on disk.

    *.tmp temperature

    How many: 1 to infinite. This run: 1. Example: Tmp1.Tmp.

    This is measured daily maximum and minimum temperature. One or more tmp files, matching NTGAGE in file.cio. Open the example file in the verification folder to see that layout on disk.

    *.slr solar radiation

    How many: 0 to infinite. This run: 1. Example: slr.slr.

    This is daily solar radiation. Usually one file named in file.cio. Additional slr files only if you split stations. Open the example file in the verification folder to see that layout on disk.

    *.hmd humidity

    *.wnd wind

    *.cst forecast

    ATMO.ATM

    *.sub subbasin

    How many: 1 to infinite. This run: 7. Example: 000010000.sub.

    This is one subbasin: area, location, and which reach it feeds. One .sub file per subbasin. A watershed needs at least one. Open the example file in the verification folder to see that layout on disk.

    *.rte channel routing

    How many: 1 to infinite. This run: 7. Example: 000010000.rte.

    This is the main channel in a subbasin: length, slope, and banks. One .rte file per subbasin that routes flow. Open the example file in the verification folder to see that layout on disk.

    *.pnd pond

    How many: 0 to infinite. This run: 7. Example: 000010000.pnd.

    This describes ponds or wetlands in a subbasin. One .pnd per subbasin. Unused ponds are zeros, not missing types. Open the example file in the verification folder to see that layout on disk.

    *.swq stream water quality

    How many: 0 to infinite. This run: 7. Example: 000010000.swq.

    This holds in-stream nutrient and algae parameters for a subbasin channel. One .swq per subbasin when water quality is on. Open the example file in the verification folder to see that layout on disk.

    *.wgn weather generator

    How many: 0 to infinite. This run: 7. Example: 000010000.wgn.

    This holds monthly climate statistics for a subbasin. One .wgn per subbasin. Used to fill missing weather. Open the example file in the verification folder to see that layout on disk.

    *.wus water use

    How many: 0 to infinite. This run: 7. Example: 000010000.wus.

    This describes irrigation or withdrawals in a subbasin. One .wus per subbasin. Unused demand still leaves a small file. Open the example file in the verification folder to see that layout on disk.

    *.hru HRU

    How many: 1 to infinite. This run: 31. Example: 000010001.hru.

    This is one hydrologic response unit: a unique mix of land use, soil, and slope. One .hru file per HRU. A run needs at least one.

    *.mgt management

    How many: 1 to infinite. This run: 31. Example: 000010001.mgt.

    This is the planting, tillage, and harvest calendar for one HRU. One .mgt file per HRU, matched to the .hru of the same ID. Open the example file in the verification folder to see that layout on disk.

    *.sol soil

    How many: 1 to infinite. This run: 31. Example: 000010001.sol.

    This is the soil profile for one HRU. One .sol file per HRU. Layer thickness and texture control infiltration and erosion. Open the example file in the verification folder to see that layout on disk.

    *.chm soil chemistry

    How many: 0 to infinite. This run: 31. Example: 000010001.chm.

    This holds nutrient and carbon starting values for one HRU. One .chm file per HRU when nutrient cycling is simulated. Open the example file in the verification folder to see that layout on disk.

    *.gw groundwater

    How many: 0 to infinite. This run: 31. Example: 000010001.gw.

    This sets shallow-aquifer properties for one HRU. One .gw file per HRU. It controls how water returns as baseflow. Open the example file in the verification folder to see that layout on disk.

    *.sdr tile drain

    How many: 0 to infinite. This run: 31. Example: 000010001.sdr.

    This describes tile drainage for one HRU. One .sdr file per HRU. Unused drainage stays at defaults. Open the example file in the verification folder to see that layout on disk.

    *.sep septic

    How many: 0 to infinite. This run: 31. Example: 000010001.sep.

    This describes on-site septic wastewater for one HRU. One .sep file per HRU. Many rural units leave defaults. Open the example file in the verification folder to see that layout on disk.

    7. After the first success

    Once output.rch is written, you can open output.sub and output.hru the same way, or bring the reach file into SWAT Check. Building a new watershed is ArcSWAT or QSWAT plus SWAT Editor; that is a different lesson. This one stops at a verified CLI run of SWAT2012 Rev. 695.
